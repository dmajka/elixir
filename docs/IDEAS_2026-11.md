## 2. The phaser: why it costs more, and the cleanup (agreed: Phase 10)

Two separate 4-stage all-pass chains (one a side), 64-bit multiplies, a clamp after every stage, the coefficient
every sample. The flanger and ring mod are one read or one multiply a sample.

| Change | Saves | Sound |
|---|---|---|
| One mono chain; L = dry + wet, R = dry − wet (interleaved notches, the classic stereo phaser trick) | ~half | different stereo image (A/B it) |
| Clamp only the feedback (all-passes keep the level) | ~15–20% | none |
| 32-bit math (states in sample units, coefficient Q14) | ~25% | inaudible |
| Coefficient every 8 samples | small | none at phaser rates |

Together ~11% → ~4–5%. **Done (Phase 10):** ~4.5% estimated (96 device instructions a stereo sample against ~236 + 2
divides); the 32-bit math was dropped (pi32v2 multiplies 32 × 32 → 64 at no extra cost; Q14 overflowed). Details in
the TO_DO file.

## 3. Effects

### Agreed (Phases 11–14)
- **GRAIN** delay mode (Clouds-style texture on the existing 64 KB line), **SHIMMER** reverb model, **FOLLOW**
  (envelope follower) global LFO wave, **SHIFT** (frequency shifter) FX bus type. designs in the TO_DO file (Phases 10–15).

### Parked ideas (cheap to medium)
- **VOWEL** DJ type: 2–3 band-passes on formant tables, FILT morphs a-e-i-o-u. ~5%, ~1 KB. Makes kicks and toms talk.
- **Bus bit/rate crush per send** (the dirt code on the FX send only). ~0.5%.
- **GRAIN FREEZE** if not in Phase 13: stop writing the line, grains keep playing (Clouds' freeze).
- **Track-hit triggers for the global LFOs** (TRIG = D1 … HH): an LFO in ONE mode becomes an AD envelope fired by a
  hit. Tiny. (See §5.)
- **MONO / PING PONG to ~110% feedback** through the tape soft clip (the dub note in the TO_DO file).
- Not for this hardware: convolution, spectral freeze, anything FFT-based (RAM and CPU).

### Clouds notes
Mutable Instruments Clouds (Émilie Gillet, MIT licence, compatible with GPL-3.0) runs granular playback on a 1–4 s
buffer at 32 kHz with up to ~40–60 grains; ports (Daisy, various Eurorack DSP modules) keep 1–2 s and fewer grains.
Elixir's version is written from scratch on the delay's line (0.74 s at 44.1 kHz): 6–8 grains is the target. What
makes Clouds sound like Clouds: random grain position and pan, a smooth window, pitch per grain, a **feedback**
path, then a diffuser/reverb after it (ECHO > REV plays that role here), and FREEZE.

## 4. Scene morph vs the kit morph you already have

**Most of a "scene morph" already exists.** MORPH blends the edit buffer with the morph target kit (LOAD > MORPH,
CC 125) over every sound parameter, and the global LFOs push it. The parameters excluded from the blend stay the
kit's: the outputs, the modulation targets, FX type, reverb model, the voice models, LFO modes, delay pitch, dirt
modes.

What a scene morph would add on top (none planned):
1. **Performance state, not just the kit:** the DJ filter (and its type), DENSITY, the global LFOs' depths, macro
   values, master comp, mutes. These live in the project, so today morph can't reach them. This is the genuinely new
   part: ~100 B RAM a scene, ~1.5 KB flash.
2. **Snapshots without saving a kit:** "SNAP" puts the sound as it is now into the morph target in one press, and
   "SWAP" exchanges A and B. Both are cheap (~200 B flash; `kit_save_ram`'s mixture already exists).
3. **More than two points:** 4 scenes on one knob (A→B→C→D). RAM is a kit copy (476 B) a scene.
4. **The discrete parameters switching at the midpoint** (FX type, reverb model) as an option. Risky: clicks.

Drafted as Phase 15 in the TO_DO file for review. Verdict: only (2) is clearly worth it soon. (1) is worth it if you want morph to move the DJ filter and density
together with the sound; but global LFOs on MORPH + DENSITY (what you're doing) already cover much of that.

## 5. Envelope follower vs "envelope-driven modulation"

Same family, three different things:
- **X-MOD (exists):** a voice's output envelope (`venv`) modulates *another voice's* filter or gain. Voice-to-voice,
  inside the kit.
- **FOLLOW wave (agreed, Phase 11):** a global LFO whose output *is* a voice's (or the mix's) level, so a hit can
  push any global destination: the kick ducks the reverb, the snare opens the DJ filter, the hats push density or
  morph. It follows the real sound (velocity, decay, choke, ratchets).
- **Hit-triggered one-shot (parked, §3):** an LFO in ONE mode fired by a track's hit: a clean AD shape of your
  choosing, independent of how the sound decays.

"Envelope-driven modulation" in the earlier top-5 meant the general idea; FOLLOW is the concrete build.

## 7. Generative track modes (research; parked)

Existing: Euclid, Turing, cellular, Grids-style, melody. Sequencer modes cost flash (~1–2 KB each) but no audio CPU.

- **ANSWER / complement:** a track that plays where another doesn't (or inverts it, or echoes it a step later with
  a chance). Call-and-response between kick and percussion.
- **Split loop lengths (Kria-style):** separate lengths for trigger, velocity, probability and lock lanes, so they
  drift apart and realign (polymeter inside one track).
- **Markov LEARN:** record a bar of what you play, then improvise in its style (transition table of steps / notes).
- Others to consider: **L-system / rewriting** patterns; **gravity / bouncing ball** (accelerating ratchets);
  **rain** (Poisson hits with density); **mutation on repeat** (each pass changes N steps, with a lock to keep the
  good ones).

## 10. Morph kit as a global LFO destination (maybe someday; asked 2026-11-15)

An LFO stepping PERFORM's **Morph kit** (VP_MKIT), the target kit itself, not the MORPH amount (GD_MORPH already
does that). Possible and not much code; how it should *behave* is the open part. Not planned.

**Wiring (~40–60 lines plus the screen and the manual):**
- `GD_MKIT` added at the end of the `GD_*` enum (perform.c), so saved destinations keep their numbers; GD_ORDER /
  GD_FULL (ui.c), the short names (ui_draw.c), the `NGD == 40u` assert.
- One of the either-way destinations (`gl.bi`, as TRANSPOSE): the ISR only works out an offset.
- The main loop applies it, as `glfo_morph` (ui.c): the knob's entry (`mk_pos()`) ± N kits through `mk_step()`
  (missing library kits and Init slots passed over), then `mk_load()`. The main loop because a library kit is a
  flash read.

**Decisions first:**
1. **It steps.** Each step swaps the whole target: with MORPH above 0 every step is a jump; at 100% it is a kit
   sequencer (maybe the point). Smoother: change the target only while it's inaudible (the MORPH amount near 0) and
   let MORPH fade the new one in.
2. **Range.** Suggested ±127 depth = ±8 (or ±16) kits. The list runs slots → library → factory, so a big depth
   crosses parts.
3. **The knob's own kit is lost.** `mk_load` throws away an edited morph kit or a SNAP (Snapshot isn't a list entry):
   one cycle and it's gone. Keep a copy to come back to (a kit, 398 B of RAM), or don't move while the source is
   Snapshot.
4. **Pacing.** A fast LFO means many flash reads or factory decodes: at most one load per `MK_REST_MS` (250 ms), or
   per 16th.
5. **Switches flip.** The non-morphing parameters come from the morph kit (`morph_mix`), so they change at each step.

Suggested if built: relative to the knob, ±127 = ±8 kits, at most one load a 16th, the knob's kit kept and restored
exactly.

## 11. Remote mute lights: polarity and colours (declined for now; asked 2026-11-17)

One user, a Launch Control XL mk2 owner, asked three times. He wants:
1. the mute pads inverted: a pad lit while its track **plays** and dark when muted ("think of them as unmutes"),
   with 0–63 muting and 64–127 unmuting;
2. Elixir's feedback to send **124** for a playing track and **3** for a muted one. On the mk2 the value it receives
   sets the LED's colour (16 × green + red + flags 12), so 124 decodes as full green and 3 as full red;
3. or, as a general version, Elixir to learn the values a pad sends and send those back.

**How it works now** (`remote.c`)
- Mutes and solos come in only on the remote's TRACKS channel: CC (or note) 104–110 mute and 112–118 solo, for D1 ..
  OH (111 and 119: the selected track). `midi_message` hands both remote channels to `remote_in_post` **before**
  `midi_cc`, so the CC map never sees them.
- The library's CC map (`kset.ccmap`, library commands 0x50 / 0x51, the Controllers page) only points a CC at a sound
  parameter (`midi_param`). It has no entry for a mute, no inversion and no say over feedback. Overriding it from the
  library can't do this, and stretching it to would mix two separate systems.
- Input (`rm_button`): CONFIG → REMOTE **Mute/solo** (`kset.rknobs & RK_TOGGLE`). PRESS (the default): any press
  flips the mute. TOGGLE: any value above 0 mutes, 0 unmutes.
- Feedback (`remote_service`, `rm_state`): 127 while muted, 0 while playing, sent as whatever the button last sent (a
  CC or a note). On the mk2, 127 shows amber and 0 dark: lit = muted, which is his "backwards".
- The mk2 template stores separate **off** and **on** values and a toggle flag for each button
  (`web/controllers/src/devices/novation/launch-control-xl-mk2/codec.ts`).

**The answer that needs no firmware.** Set the mute pads to **momentary** and leave Mute/solo at **PRESS**. Elixir
then owns the mute state and drives the lights, so what the pad sends doesn't matter, nothing can be backwards, and
mutes made on the FM-1's panel stay in sync. All he loses is his colour choice: muted shows amber, playing dark.
With **toggle** pads the controller keeps its own toggle state, which (we believe) the feedback doesn't change, so a
mute from the panel puts the pad out of step and its next press sends the wrong value. If he insists on toggle pads,
on = 0 / off = 127 in the template should flip the input (if Components allows on below off), but the lights still
show muted.

**Why not "learn the values"**
- In PRESS mode with momentary pads the values are only press (127) and release (0): there's nothing to learn.
- With toggle pads nothing is learned until each pad has gone both ways, and it's lost at a restart unless saved.
- A pad sending 3 for "off" counts as a press today. That's why he also asks for a 0–63 threshold, and changing that
  could break controllers that send small values for "on".

**Options, if it's ever built** (estimates, not built)
| Option | Flash | RAM | Notes |
|---|---|---|---|
| A. "Lit = PLAYING" switch for the mute row | ~300–500 B | 0–4 B | Swaps the two values sent. Needs a knob: REMOTE's four are taken, so a second REMOTE page |
| B. A colour preset (PLAIN 127/0, LCXL COLOURS) | ~300–600 B | 0–4 B | Same knob problem. Don't ship red/green: see below |
| C. Light values per row (on, off: 0–127), set from the Controllers page | ~150–250 B firmware + web | 0–4 B | No knob: a library command writes the settings. Works for any controller (Launchpads pick colours by value too). The page could set the colours and the template in one go |

The settings have room: new bytes go at the end of `elixir_settings_t` (it already handles longer versions by
length), or in its padding.

**Budget then** (the 2026-11-17 build, with KEYS folding): flash 574,252 B of the 581,564 B app slot (**7,312 B
free**); RAM `.data` + `.bss` 57,688 of 73,728 B; pool 370,828 of 380,928 B; `.ram_text` 288 B free.

**Accessibility.** Red/green colour blindness is common, so a red/green pair shouldn't be the only difference
between two states of one button. Elixir shouldn't offer or suggest one, and option B as asked is out. Option C only sends the two numbers the user picks, so users can choose
lit/dim or amber/off just as easily.

**Decision (2026-11-17): not now.** It's a permanent setting for one user and one controller, and the momentary +
PRESS setup fixes most of the complaint. Flash isn't the blocker (half a kilobyte is affordable), but it's tight.
**Revisit if** others ask for custom remote lights or a lit-while-playing mute row. Then build **C**. Its defaults
stay 127/0, so nothing changes for anyone who doesn't set it. Maybe add A as a checkbox beside it, rather than a new
knob on the device.

**Reply to send** (or sent): "Set the mute pads to momentary (not toggle) and leave Elixir's Mute/solo at PRESS:
Elixir then owns the mute state and the lights, so the direction can't be backwards and panel mutes stay in sync. The
lights show amber while muted and dark while playing. Custom colours aren't planned for now."
